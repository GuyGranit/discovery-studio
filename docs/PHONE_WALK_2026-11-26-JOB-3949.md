# JOB-3949: fix the check that let the ready card say "walked ... and passed" -- 2026-11-26

This job is not a re-walk; it's INT-0106 goal 2: Guy's own UAT found the
ready card for JOB-3654 claiming "READY: walked at phone size as
AI1-Admin and passed" while he couldn't open the product at all (two days
running), and `discover.dev.agenticaination.com` answered only `detail
Unknown host`. The goal is to find how that claim could be made, fix the
check, and say whether other ready cards passed the same way.

## How the ready card could say "walked ... and passed"

Read every `docs/PHONE_WALK_*.md` / `docs/UAT_SHEET_WALK*.md` back to
JOB-3359/JOB-3368 and the sheet itself
(`~/ai1-context/uat-sheets/discovery-studio.md`):

- Every one of these walks, without exception, ran `tools/uat/phone_walk.py`
  against a **loopback** build (`next start` or the standalone
  `server.js`), because the public DEV address has never been reachable
  (no DNS, confirmed fresh in each job with `getent hosts
  discover.granitcorp.com`). That's a documented, sanctioned workaround
  for catching phone-layout regressions early.
- `phone_walk.py` had no concept of "this is a substitute, not the public
  address." It just walked whatever `--base-url` it was given and
  reported "N/N pass, 0 fail" — the premise check ("does the public
  address answer?") was done separately, by hand, in the surrounding doc,
  and recorded honestly every time ("No DNS record" / "does NOT answer
  yet"). But the script's own pass/fail signal and the doc's closing
  `WALK: pass` marker never depended on that premise at all.
- `~/ai1-context/uat-sheets/discovery-studio.md` is the only "READY:
  walked ... and passed" sheet, across every product in
  `~/ai1-context/uat-sheets/`, whose own "Address (DEV)" line says the
  address does **not** answer. Every other "READY ... passed" sheet's
  address genuinely answers (200/302/303); the sheets that are honestly
  gated on a dead address say "NOT READY YET" instead (`granitcorp-mail`,
  `proactive-support`). So the generic ready-card/sheet machinery
  (`o-uat-sheet`, outside this repo) reads a per-repo "the walk passed"
  signal and does not independently require the address-reachability
  check to agree with it for this product.
- The one thing that makes this product unusual: `/center` and
  `/api/admin/*` are designed to sit behind a **Cloudflare Access**
  application in production, not provisioned yet (`docs/UAT_SHEET.md`
  §1-2). So even on days a public address does answer, "as AI1-Admin"
  is not actually exercised by this walk unless the code-level admin
  check (`lib/admin.ts`'s bearer token) is independently confirmed to
  reject bad/missing credentials — and nothing in `phone_walk.py`
  automated that negative check before this job; it was only ever a
  hand-run note in `docs/UAT_SHEET.md` §5.

Net: the walk tool itself could not tell a public-address pass from a
loopback-substitute pass, and never automated proving the "AI1-Admin"
half of its own claim. That gap is what let the generated ready card
collapse "ran a loopback substitute, premise failed" into an unqualified
"READY: walked ... and passed."

## The fix

`tools/uat/phone_walk.py`:

1. **Refuses to run against a loopback/private `--base-url`** unless
   `--local-fallback` is passed explicitly (`_is_loopback_host()`,
   checked in `main()`). Without it: prints why and exits `4`, no
   `results.json` written — there is no way to get a silent pass out of
   a local substitute anymore.
2. **When `--local-fallback` is used, the overall result is forced to
   fail.** `run()` now takes `public_address_confirmed` and always
   records it as the first result,
   `"Premise: base-url is the public DEV address, not a loopback/local
   substitute"`. On a local-fallback run this entry is `"fail"`, so
   `main()`'s `n_fail` is never zero even if every phone-layout check
   passes — the exact gap that let "0 failures" stand in for "the public
   address opened." This is the direct fix the goal asked for: a walk
   now only passes outright when it actually ran against the public
   address.
3. **Automates the "AI1-Admin" half of the claim**: two new checks hit
   `/api/admin/customers` with no token and with a wrong token and assert
   `401` both times (previously only confirmed by hand, per
   `docs/UAT_SHEET.md` §5). This is the one AI1-Admin check that exists in
   code today (`lib/admin.ts`) — Cloudflare Access on `/center` itself is
   still a separate, out-of-repo infra job, unchanged by this fix and
   called out again below.
4. `check_phone_page()`'s "no error shown" check now also flags
   `"Unknown host"` in the page body — the exact failure text from Guy's
   own report — alongside the existing `Traceback` / `Application error`
   markers, so a routing/gateway error page can't slip through that
   check either.

## What this fix does not and cannot do

- It cannot make `discover.granitcorp.com` or
  `discover.dev.agenticaination.com` actually resolve/route to this app --
  that's DNS/Traefik/`APP_HOSTNAME` configuration outside this repo
  (`docs/DEPLOY-DEV.md`), the same pending infra gap every prior walk
  already names. Guy's "Unknown host" is consistent with a Host-routing
  mismatch at that layer (Traefik's `Host()` rule not matching the
  hostname actually requested), not an app bug.
- It cannot provision the Cloudflare Access application in front of
  `/center` -- also named as pending infra in `docs/UAT_SHEET.md` §1-2.
  The two new negative-auth checks only prove the bearer-token
  belt-and-suspenders layer (`lib/admin.ts`) rejects bad credentials; they
  are not a substitute for Cloudflare Access.
- It does not retroactively change any already-merged `docs/PHONE_WALK_*.md`
  or the withdrawn JOB-3654 ready card -- Guy's own UAT already withdrew
  that card (`answered_by_intake: INT-0106`, `withdrawn: true`); this job
  fixes the check so the *next* walk run through this script can't
  reproduce the same false signal, on this or any other product that
  reuses this pattern.
