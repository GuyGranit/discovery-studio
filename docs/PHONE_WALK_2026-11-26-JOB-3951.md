## 2. The real address answers, but behind Cloudflare Access for every path

`discover-dev.agenticaination.com` is live and reachable from outside AI1
— that is real progress over "cannot open the product at all." But every
path tried, including `/` (the plain landing page, not just `/center`),
redirects to a Cloudflare Access login ("Log in to Discovery Studio DEV",
sign-in method "Cloudflare" — a one-time PIN). Per `APPS.yaml`'s own note,
that Access application is scoped to **guy@granitcorp.com only, for now**.

This is wider than the app's own code assumes. `lib/admin.ts`,
`app/center/actions.ts`, `.env.example` and `docs/UAT_MANUAL.md` all say
Cloudflare Access was only ever meant to sit in front of `/center` and
`/api/admin/*` — the operator console — leaving `/` and `/session/<token>`
(the customer-facing pages) open to anyone holding a one-time pass link,
with the bearer-token check in `lib/admin.ts` as the only gate on the
admin API. What's actually provisioned gates the **whole hostname**.

Consequence: today, nobody except guy@granitcorp.com can reach the
Discovery Studio landing page at all — not a real customer with a paid
pass link, and not this job's own outside-AI1 walk. `ADMIN_PROBES.yaml`
already documents this as expected for Cloudflare-Access-fronted apps
generally ("a plain outside sign-in cannot pass it"); it isn't a new kind
of failure, but discovery-studio's customer-facing pages were never
supposed to be behind it at all.

This job has no Cloudflare Access credential for any identity, and
correctly so — an outside builder job guessing or working around an
Access gate is not something to do quietly. So this walk could not carry
a real session through the public address past that login screen. Every
step after it (steps 3-5 below) is evidence from the same code running
locally, not from the public address.

## 3. The discovery flow itself, verified for real (local build, not the public address)

Built the app fresh from this job's branch (`npm install`, `npm run
build` — Next.js `output: "standalone"`), ran the standalone server on
loopback with a throwaway `ADMIN_API_TOKEN` (generated locally, never
printed, never the AI1-Admin password), and ran the existing phone-size
(390x844) UAT runner (`tools/uat/phone_walk.py`) against it end to end:
operator issues a pass in `/center` → customer opens the one-time
`/session/<token>` link → two follow-up turns of the interview → "End
session" → summary.

**Result: 42/42 checks passed, 0 failures.** Screenshots and
`results.json`: `docs/uat/phone-walk-2026-11-26-JOB-3951-local/`.

What "reach the summary" means today, confirmed against
`docs/UAT_MANUAL.md` §4 and `components/SessionClient.tsx`: ending a
session shows tokens used, cost, and pass state
(`07-session-ended.png`) — there is no separate "requirements summary"
document shown to anyone (customer or Guy); the ten-section spec
(`lib/spec.ts`) is tracked and shown only as a live coverage percentage
during the interview (`05-session-turn-1.png`: "Spec coverage: 10%").
That matches the product as built, not a gap found by this walk.

This confirms the discovery flow itself has no regression — the only
thing standing between "it works" and "a customer on the real address can
use it" is the Cloudflare Access scope described in §2.
