# JOB-3950: AI1-Admin sign-in, no per-product password -- 2026-11-26

INT-0106 goal 3: "Entry as AI1-Admin without a password, as on the other
products." Guy's own UAT on DEV (25 Nov) found Discovery Studio has no
AI1-Admin sign-in at all -- `/center` was wide open with zero gate (only
the separate `/api/admin/*` routes checked a bearer token), while the
generic sheet/ready-card boilerplate and `~/ai1-context/APPS.yaml`
(`o-apps show discovery-studio`: `master_admin: ai1-admin@granitcorp.com`)
both say the product should accept AI1-Admin sign-in like every other app.

## What "without a password" means here

Checked the actual convention on sibling products (carmitdl, realai,
itcost, print3d, smb-crm) and the org rule behind it
(`~/ai1-context/INCIDENT_AI1_ADMIN_2026-10-22.md`, decision 141,
mechanised by `o-apps master-admin`): every app with a login accepts
`ai1-admin@granitcorp.com` as master admin, checked against **one shared
secret** delivered via Integrations (`other:ai1-admin`, field `api_key`)
and pushed into each app's own env var by `o-secret-push`. "Without a
password" means without a *new, per-product* password Guy has to create
or remember -- not a zero-credential/header-trust bypass. No sibling
product relies on Cloudflare Access header-trust for this; that remains a
separate, still-unprovisioned production hardening layer for this app
specifically (`docs/UAT_SHEET.md` §1-2), unchanged by this job.

## The fix

- `lib/admin.ts`: added `AI1_ADMIN_EMAIL`, `verifyAi1AdminLogin`,
  `ai1AdminSessionToken`, `isAi1AdminSession` -- checks
  `ai1-admin@granitcorp.com` plus the new `AI1_ADMIN_PASSWORD` env var
  (timing-safe compare), and derives a stateless session-cookie token by
  HMAC-SHA256 of the admin e-mail under that same secret (no session
  store needed; changing the secret invalidates every outstanding
  session). `isAdmin()` (the existing bearer-token gate for
  `/api/admin/*`) is untouched.
- `app/center/page.tsx`: reads the session cookie; renders an AI1-Admin
  sign-in form (e-mail pre-filled, password field) when it's missing or
  invalid, the existing console when it's valid, plus a "Sign out"
  button.
- `app/center/actions.ts`: new `adminLogin` (verifies credentials, sets
  an httpOnly `discovery_studio_admin` cookie, redirects to `/center`;
  wrong credentials redirect to `/center?error=1`) and `adminLogout`
  (clears the cookie). `activatePass` now also checks the session itself
  -- Next's own guidance treats a Server Action like a public endpoint,
  since it's callable independently of which UI branch rendered the form
  that points at it.
- `.env.example`, `docs/UAT_SHEET.md` §2/§4, `docs/UAT_MANUAL.md`,
  `docs/DEPLOY-DEV.md`: documented `AI1_ADMIN_PASSWORD` and the new
  sign-in step. Left every dated `docs/PHONE_WALK_*.md` /
  `docs/UAT_SHEET_WALK*.md` / `docs/ACCEPTANCE-CARD-*.md` alone --
  historical walk records, not living docs.
- `tools/uat/phone_walk.py`: Step 1 now signs in via
  `--admin-password` / `AI1_ADMIN_PASSWORD` before touching the console;
  Step 2's submit-button selector was narrowed from the ambiguous
  `button[type="submit"]` to `button:has-text("Payment received")` --
  `/center` now carries a second submit button ("Sign out"), and the bare
  selector matched it first, silently logging the walk back out mid-step
  (see "One real bug found" below).
- `tests/admin.test.ts` (new): `verifyAi1AdminLogin` /
  `ai1AdminSessionToken` / `isAi1AdminSession` accept the right
  credentials, reject everything else, reject when the secret is unset,
  and reject a session minted under a since-rotated secret; a second
  block re-confirms the untouched bearer-token gate.

## One real bug found and fixed mid-job (not a pre-existing regression)

First full walk after wiring the login form: 20/26 passed, with the
"activate pass" step mysteriously landing back on the sign-in screen.
Root cause, found by scripting the exact Playwright steps standalone and
inspecting cookies/requests: `/center` now has two `button[type="submit"]`
elements -- the new "Sign out" button renders first in the DOM, so the
walk's old selector (written back when "activate pass" was the only
submit button on the page) clicked *that* one, logging the session out
mid-step instead of issuing the pass. Fixed in `tools/uat/phone_walk.py`
(selector above); not an app bug, confirmed by directly checking
`ctx.cookies()` across the real submit (unaffected) and the login
page rendering correctly once the walk clicks the intended button.

A second, unrelated harness issue surfaced during debugging: running
`next build` then `node .next/standalone/server.js` straight (without
copying `.next/static` into `.next/standalone/.next/static` first, the
`Dockerfile`'s own step) 404s every CSS asset, which is why the first raw
attempt also showed bogus 21px tap targets on *both* the sign-in and
console forms. Every walk doc back to JOB-3841 already does this copy
step correctly; this job's own early debug runs just skipped it before
settling on the documented procedure (used for the recorded runs below).
